# v2.1.1 — Protect ancestor tapes and improve verification

This release fixes the issues found in the v2.1.0 review and adds explicit eject
support inside a waiting operation's cartridge prompt.

- **Protect earlier backups in the restore chain.** New backups carry ancestor
  IDs in their volume headers and catalog summaries. Prompted wipes refuse an
  older full or incremental required by the active backup, even on another
  cartridge and after restarting the application.
- **Handle incomplete ancestry conservatively.** Older full backups can start a
  complete ancestor list. Older incrementals remain readable and appendable, but
  recorded-media wipes at the prompt are refused when every ancestor cannot be
  identified. Use blank spares for those jobs. The list is bounded to 512 IDs;
  exceeding that bound disables recorded-media wipes rather than blocking backup
  or silently dropping protection. A new full starts a complete list again.
- **Reject wrong cartridges sooner.** When a complete current catalog does not
  contain the requested ID or volume, validate its endpoints and reject the tape
  without scanning the archive. Partial/missing catalogs retain their fallback.
- **Make verification progress accurate.** `backup --verify` and
  `zfs-backup --verify` use one total bar for writing and read-back and keep the
  drive lock through both. Verification uses the committed archive size. The bar
  cannot show 100% before read-back succeeds. Failure/interruption identifies the
  already committed backup; standalone `verify` now advances its bar and ETA
  from verified archive payload bytes.
- **Eject without stopping the job.** Type `eject` at a manual cartridge prompt
  to unlock and unload. The operation retains its buffered data, drive lock, and
  requested volume. Insert the replacement and press Enter. Unload errors return
  to the prompt. No automatic ejection is introduced.

The tape formats and SSH protocol are unchanged. Ancestor fields are optional
metadata extensions; existing archives remain restorable. This update does not
change an already-running process or give its existing prompt new commands.

Validation includes simulated multi-cartridge backup/restore with prompted
ejection, ancestry protection across sessions, old-metadata compatibility,
catalog lookup and fallback, verification failure/interruption, real GNU tar/SSH,
standalone binary/terminal checks, Debian 11 without Python, and native OpenZFS
scratch-pool tests in CI. Physical tape hardware was not available.

The Linux x86-64 executable bundles Python and requires glibc 2.31 or newer.
See the [README](https://github.com/lbadger/tape-backup/blob/v2.1.1/README.md)
for usage and compatibility details.
