# v2.0.0 — Native ZFS streams and safer tape workflows

Back up existing ZFS filesystem snapshots directly with `zfs-backup`, and receive
full or incremental chains with `zfs-restore`. File backups gain exclusions,
incrementals always append, and both restore paths support a whole chain or one
incremental at a time. Running the executable without arguments now shows command
help with file and ZFS examples.

## New workflows

```bash
# File and folder exclusions are relative to --source.
./tape-backup backup --source /opt --exclude cache --exclude 'logs/*.log'
./tape-backup backup --source /opt --exclude-from /root/backup-excludes.txt

# Send existing snapshots; keep the previous source snapshot for incrementals.
./tape-backup zfs-backup --snapshot tank/books@full
./tape-backup zfs-backup --snapshot tank/books@next --base FULL_ID
./tape-backup zfs-restore --backup FULL_ID DELTA_ID --dataset tank/recovered

# Inspect drive state without moving the tape; request verified JSON backup results.
./tape-backup status
./tape-backup backup --source /opt --json --verify
```

- `--exclude` and `--exclude-from` work for local and SSH file sources.
  Incrementals inherit the parent's exclusion policy; changing it requires a new
  full backup.
- Native ZFS supports one existing filesystem snapshot, full/incremental sends,
  SSH sources, compressed records, and encrypted raw streams via `--raw`.
  Snapshot GUIDs identify the baseline. Recursive replication and zvols are not
  included in this release.
- ZFS restore verifies all selected backups before receiving them, requiring two
  tape passes. It never requests forced rollback and leaves the destination
  unmounted and read-only, with sharing disabled. Preserve encryption keys
  separately and keep the restore baseline unchanged between incrementals.
- `inspect` lists the cartridge's backup catalog with fewer seeks. `status` and
  `doctor` report drive state. `list` reads tar member names without extraction.
- `wipe`, `eject`, and `compression status|on|off` make cartridge management
  explicit. Tape-change prompts pause progress logging; wrong read cartridges
  can be replaced without restarting the restore.
- Backup `--json` reports archive and metadata completion, append readiness, and
  warnings. `--verify` reads the completed backup back before reporting verified
  success. Drive locks cover tape-mode aliases and different user accounts.

## Upgrade notes

- **Full backups now require blank cartridges**, as do continuations. Reuse used
  media only through an explicit `wipe`; pressing Enter at a load prompt cannot
  authorize overwriting recorded data. Media-command loaders receive `blank` for
  a full backup's first cartridge as well as continuations.
- Incrementals append automatically. `--append` remains an optional compatibility
  flag. Incomplete or ambiguous recorded tails are refused.
- **Update both SSH endpoints.** The new helper protocol rejects older helpers
  instead of silently ignoring exclusion or ZFS options.
- Released v1.0.0 **format-3 tar tapes remain readable**. New native ZFS volumes
  use format 4 and require v2.0.0. Unused pre-v1 formats are no longer supported.
- Physical `inspect` requires `--scan` to fall back to reading an entire cartridge
  when no usable catalog exists. Partial inspection returns nonzero while
  preserving discovered entries in JSON. `inspect --first` reads one header.
- Native restores require a new child dataset for a full backup. An interrupted
  receive can leave an incomplete dataset; rebuild into a separate destination.

The Linux x86-64 executable is built against glibc 2.31 and bundles Python.
GNU tar is required for file workflows; OpenZFS is required on a native source
or receive host. Verify the download with `sha256sum -c tape-backup.sha256`.

## Validation

- Main suite: 208 tests, with 204 passing and four opt-in tests skipped. The
  three native kernel tests and the 10 GiB test passed in separate runs below.
- Source, simulated cartridge, real GNU tar/SSH, and standalone executable tests.
- Verify and restore an actual tape fixture produced by the v1.0.0 executable.
- Native full, incremental, stepwise, encrypted raw, and standalone executable
  round trips on OpenZFS 2.2.2 in an isolated Ubuntu 24.04 VM.
- Standalone executable smoke tests in Debian 11 without Python installed.
- A 10 GiB backup/verify/restore round trip through the standalone executable,
  with the 10 GiB buffer setting and a restored SHA-256 comparison.
- GitHub CI repeats the build, source/binary tests, and native ZFS scratch-pool
  tests before publication.

Physical tape hardware was not available for this validation. Cartridge
simulation and the test capacity limit exercise rollover and replay, but do not
replace scratch-tape qualification of a particular drive and loader.
